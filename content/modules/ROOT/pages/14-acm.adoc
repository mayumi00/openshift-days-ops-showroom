== 複数環境における Red Hat OpenShift クラスターおよび仮想マシンの作成と管理

セットアップから日常運用にいたるまでクラスターを自ら制御することで、ワークロードやデータの配置場所の決定、独自のポリシー設定、およびコンプライアンスの遵守が可能になります。これにより、各種規制への迅速な適応、ビジネスの柔軟性維持、および外部プロバイダーへの依存回避が実現します。クラスターと仮想マシンを柔軟に管理することで、最初からセキュリティとコンプライアンスのニーズに適合したクラウドを構築できます。

=== RHACM 管理クラスターの概要

Red Hat Advanced Cluster Management (RHACM) は、OpenShift クラスターのフリート全体を管理するための、クラウド環境における中央集権的なコントロールプレーンとして機能します。マルチ環境にわたるクラスターライフサイクル管理、仮想マシン管理、ポリシー適用、アプリケーションデプロイ、およびオブザーバビリティ（可視性）のための単一の管理拠点と統一インターフェースを提供します。

=== Kubernetes クラスターの作成と管理

Red Hat Advanced Cluster Management for Kubernetes (RHACM) は、新しい OpenShift クラスターのデプロイと管理を簡素化します。IPI や Assisted Installer などの戦略も利用可能ですが、RHACM はさらに一歩進んで、クラスター作成ウィザードを使用してわずか数クリックで新しいクラスターをデプロイできるようにします。

== RHACM コンソールを使用した仮想マシンの作成と管理

OpenShift Virtualization を備えた Red Hat Advanced Cluster Management (RHACM) は、単一のコンソールからクラスターと VM の統合された Policy-as-Code（コードによるポリシー）駆動型の制御を提供します。リソースへのラベル付け、配置の強制、およびコンプライアンスの自動化が可能になり、異なる管理ツール間を行き来する必要がなくなり、すべてのワークロードにわたって一貫した制御が保証されます。

この演習を完了すると、以下のことができるようになります。

* RHACM の検索 (Search) インターフェースをナビゲートして、フリート全体から仮想マシンリソースを特定する。
* RHACM の作成ウィザードを使用して新しい仮想マシンをプロビジョニングする。
* マルチクラスタービューから直接 Day 2 運用（停止、起動、マイグレーション）を実行する。

NOTE: あらかじめ *rhel-webserver* という仮想マシンがデプロイされていることにお気づきかもしれません。このマシンは以降の演習で使用します。削除したり電源をオフにしたりすると他のモジュールに影響を与えるため、そのままにしてください。

[[container-workloads]]
=== OpenShift GitOps を通じたコンテナワークロードのデプロイと管理

OpenShift GitOps（Argo CD および RHACM を使用）を使用すると、信頼できる単一の情報源（Single Source of Truth）として Git を使用して、クラスター全体にアプリをデプロイおよび管理できます。

Git からクラスターが更新を取得する主な方法は2つあります。
- プル (Pull) モード: 各クラスターが独自の更新を取得するため、セキュリティが高まり、すべてが特定リージョン内に保持されます。
- プッシュ (Push) モード: 中央のツールがクラスターへ更新を送信します。

このラボではプッシュモデル（Argo CD はセットアップ済み）を使用するため、異なる場所にある複数のクラスターであっても、GitOps を使用してアプリをどれほど簡単にデプロイおよび管理できるかを確認できます。

== ポリシーガードレールによるセキュリティ

*RHACM はこの目的のために構築されています！*

* **主権ポリシーのコード化** — 主権やコンプライアンスの要件を、アプリケーションコードとともにバージョン管理およびレビューされるポリシーリソースとして表現します。
* **大規模なガバナンス** — ClusterSet やラベルを使用して特定のリージョンや環境にポリシーをターゲット設定し、地域を超えた一貫性を強制します。
* **自律的な監視** — 定義されたガードレールに対する「ドリフト（乖離）」を継続的にチェックし、中央で違反を表面化させて信頼を維持します。
* **委任しつつ境界を強制** — プラットフォームチームが設定したフレームワーク内でアプリケーションチームが迅速に動けるようにし、ビジネスの自主性が組織の標準を損なうことがないようにします。

=== リージョンを持つ単一クラスターにおけるポリシーへの対処

EMEA（欧州・中東・アフリカ）における欧州連合 (EU) の一般データ保護規則 (GDPR) は、世界で最も包括的なデータ保護フレームワークの1つです。これは、EU 内で事業を展開する組織にとって多くの悩みの種でもあります。EMEA で稼働する Kubernetes クラスターの場合、GDPR はポリシーとしてコード化されなければならない特定の技術的要件を課しています。

GDPR の技術的要件のコアピラーに対処するために、3つのポリシーを EMEA クラスターにデプロイしましょう。
- **データレジデンシー（データ居住性）のラベル付け**（第44条〜第49条 — 適切な分類メタデータを持つ主権ネームスペースの存在を保証）
- **Design by Data Protection（データ保護による設計）**（第25条 — ネットワーク隔離）
- **処理のセキュリティ**（第32条 — ポッドセキュリティの強化）

=== EMEA 管理クラスターへのポリシーのデプロイ

.手順
. Fleet Management コンソールから *+* サイン -> *Import YAML* タブをクリックします。
+
image::02-rhacm-yaml.png[RHACM YAML policy editor, link=self, window=blank, width=100%]

. 次に、以下の YAML を貼り付けて *Create* をクリックします。
+
[source,yaml,subs="+macros,+attributes",role="copypaste"]
----
apiVersion: policy.open-cluster-management.io/v1
kind: Policy
metadata:
  name: policy-emea-namespace-compliance
  namespace: policies
  annotations:
    policy.open-cluster-management.io/standards: GDPR
    policy.open-cluster-management.io/categories: Data Protection
    policy.open-cluster-management.io/controls: Data Residency Labeling
spec:
  remediationAction: inform
  disabled: false
  policy-templates:
    - objectDefinition:
        apiVersion: policy.open-cluster-management.io/v1
        kind: ConfigurationPolicy
        metadata:
          name: emea-sovereignty-namespace
        spec:
          remediationAction: inform
          severity: high
          object-templates:
            - complianceType: musthave
              objectDefinition:
                apiVersion: v1
                kind: Namespace
                metadata:
                  name: gdpr-workloads
                  labels:
                    data-classification: gdpr-restricted
                    sovereignty: emea-only
                    compliance-framework: gdpr
                    pod-security.kubernetes.io/enforce: restricted
                    pod-security.kubernetes.io/audit: restricted
                    pod-security.kubernetes.io/warn: restricted
                  annotations:
                    compliance.example.com/regulation: "EU General Data Protection Regulation"
                    compliance.example.com/articles: "Article 25, Article 32, Article 44-49"
                    compliance.example.com/data-residency: "EU/EEA only"
                    compliance.example.com/contact: "dpo@example.com"
    - objectDefinition:
        apiVersion: policy.open-cluster-management.io/v1
        kind: ConfigurationPolicy
        metadata:
          name: emea-data-residency-namespace
        spec:
          remediationAction: inform
          severity: high
          object-templates:
            - complianceType: musthave
              objectDefinition:
                apiVersion: v1
                kind: Namespace
                metadata:
                  name: data-residency-emea
                  labels:
                    data-classification: gdpr-restricted
                    sovereignty: emea-only
                    compliance-framework: gdpr
                  annotations:
                    compliance.example.com/regulation: "EU General Data Protection Regulation"
                    compliance.example.com/data-residency: "EU/EEA only"
---
apiVersion: cluster.open-cluster-management.io/v1beta1
kind: Placement
metadata:
  name: placement-policy-emea-namespace-compliance
  namespace: policies
spec:
  clusterSets:
    - managed
  predicates:
    - requiredClusterSelector:
        labelSelector:
          matchExpressions:
            - key: location
              operator: In
              values:
                - emea
---
apiVersion: policy.open-cluster-management.io/v1
kind: PlacementBinding
metadata:
  name: binding-emea-namespace-compliance
  namespace: policies
placementRef:
  name: placement-policy-emea-namespace-compliance
  kind: Placement
  apiGroup: cluster.open-cluster-management.io
subjects:
  - name: policy-emea-namespace-compliance
    kind: Policy
    apiGroup: policy.open-cluster-management.io
----
image::02-rhacm-yaml-1.png[RHACM YAML policy applied, link=self, window=blank, width=100%]
+
[IMPORTANT]
====
GDPR コンプライアンスは、明確にラベル付けされたネームスペースを持つことから始まります。ラベルとアノテーションにより、ポリシーが GDPR 制限対象のワークロードをターゲットにし、監査要件をサポートし、データレジデンシーを強制できるようになります。このポリシーでは、すべての EMEA クラスターに2つのキーネームスペース（コンプライアンス用に完全にラベル付けされた `gdpr-workloads` と、厳格な EU 限定ワークロード用の `data-residency-emea`）を含めることが義務付けられています。適切なラベル付けは、規制当局に対して GDPR コンプライアンスを証明するために不可欠です。
====
+
. YAML が適切に追加され、エラーがないことを確認します。
+
image::02-rhacm-yaml-2.png[RHACM YAML policy verification, link=self, window=blank, width=100%]
+

=== マルチクラスター管理の重要なまとめ

* **中央集権的クラスター管理** — RHACM を使用して、1箇所から複数のリージョンにわたる OpenShift クラスターを作成、ラベル付け、および管理します。

* **統一されたワークロード管理** — クラスター全体の完全な可視性をもって、仮想マシンとコンテナを一緒に運用します。

* **一貫したアプリのデプロイ** — OpenShift GitOps と RHACM による Git バックエンドの自動化を使用して、複数のクラスターにアプリケーションをデプロイおよび更新します。

* **自動化されたコンプライアンス** — ポリシーをコードとして定義および適用し、データ居住性および組織の要件を満たします。
