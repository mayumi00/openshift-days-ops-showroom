== はじめに（Getting Started）

=== モジュールの概要（Module Overview）

**所要時間:** 15〜20 分 +
**形式:** ハンズオン +
**対象者:** プラットフォームエンジニア、運用チーム

include::partial$console-access.adoc[]

このモジュールでは、アプリケーションのデプロイ、外部への公開、容量に応じたスケーリング、障害発生時の OpenShift の自己修復動作の確認、およびヘルスチェックの設定を行います。これは OpenShift 上でワークロードを管理するためのコアな運用ワークフローです。

=== 学習目標（Learning Objectives）

このモジュールを完了すると、以下のことができるようになります：

* コンテナイメージからのアプリケーションのデプロイ
* TLS を使用した Route 経由でのアプリケーションの公開
* 水平スケーリングとその動作の観察
* OpenShift の自己修復（Pod の再作成）の理解
* Liveness（生存）および Readiness（準備状態）プローブの設定
* メンテナンス中の可用性を保護するための PodDisruptionBudget（PDB）の使用

== デプロイと検査（Deploy & Inspect）

=== アプリケーションのデプロイ（Deploy an Application）

プロジェクトを作成し、Web サーバーをデプロイします：

[source,bash,role="execute"]
----
oc new-project app-management
----

次に、OpenShift コンソールを使用して WeatherNow アプリケーションをデプロイします。WeatherNow は、運用トラック全体でテストワークロードとして使用されるシンプルな httpd ベースのコンテナです。

. コンソールの右上隅にある **+** (追加) ボタンをクリックし、**Container images**（コンテナイメージ）を選択します。**Select project**（プロジェクトの選択）の下で、**app-management** が選択されていることを確認します：
+
image::app-mgmt-deploy-menu.png[Add menu showing Container images option, link=self, window=blank]
. **Deploy Image**（イメージのデプロイ）フォームにて：
* **Image name from external registry**（外部レジストリからのイメージ名）を選択し、以下を入力します：`quay.io/openshift-workshop-applications/weathernow:latest`
* イメージに **Validated**（検証済み）と表示されるまで待ちます
* **Select project** が `app-management` に設定されていることを確認します
* **Name**（名前）を `weathernow` に設定します
* 下にスクロールして、**Create a route**（ルートの作成）チェックボックスのチェックを**外します**。OpenShift はルートを自動的に作成できますが、ルーティングの仕組みを理解するために手動で行います。
+
image::app-mgmt-uncheck-route.png[Create a route checkbox unchecked, link=self, window=blank]
* **Create**（作成）をクリックします
+
image::app-mgmt-deploy-image.png[Deploy Image form with weathernow image validated, link=self, window=blank]
これにより、2 つのリソースが作成されます：

* **Deployment** - 実行するコンテナとレプリカ数を定義します
* **Service** - Pod にトラフィックをルーティングする内部ロードバランサーです

image::diagrams/02_service.png[OpenShift Service Load Balancing, 500, align=center, link=self, window=blank]
Topology（トポロジー）ビューに移動します。Pod が実行中で Service が作成されていることが確認できますが、**Routes**（ルート）の下には "No Routes found for this resource"（このリソースのルートが見つかりません）と表示され、アプリケーションはまだクラスター外部からアクセスできません。

image::app-mgmt-deploy-no-route.png[Topology view showing weathernow with no route, link=self, window=blank]
ここでターミナルに切り替え、CLI 経由で同じ情報を確認します：

[source,bash,role="execute"]
----
oc get pods -n app-management
----

Topology ビューで確認したのと同じ、`Running` ステータスの Pod が 1 つ表示されるはずです。

=== アプリケーションの検査（Inspect Your Application）

次に進む前に、最も重要な 2 つの診断コマンドに慣れておきましょう。これらは任意のネームスペース内の任意の Pod に対して動作します。コンソールでもこれを確認できます。前の手順から Topology ビューが開いているはずです。ワークロードノードをクリックし、右側のサイドパネルにある **Resources**（リソース）タブをクリックします。Pod 名をクリックすると、**Details**（詳細）、**Events**（イベント）、および **Logs**（ログ）タブを備えた Pod の詳細ビューが開きます。コンソールのログビューアは、リアルタイムストリーミング、テキスト検索、およびダウンロードをサポートしています。

image::app-mgmt-topology-pod-panel.png[Topology side panel showing pod name under Resources tab, link=self, window=blank]
image::app-mgmt-pod-details.png[Pod detail page showing Overview with Events and resource usage, link=self, window=blank]
Pod の詳細情報（イベント、ノードの配置、コンテナのステータス）を取得します：

[source,bash,role="execute"]
----
oc describe pod $(oc get pods -n app-management -o jsonpath='{.items[0].metadata.name}') -n app-management | tail -15
----

下部の **Events** セクションには、何が起こったかが正確に表示されます（イメージのプル、コンテナの作成、特定ノードへの Pod のスケジューリング）。

コンテナのログを確認します：

[source,bash,role="execute"]
----
oc logs $(oc get pods -n app-management -o jsonpath='{.items[0].metadata.name}') -n app-management | head -5
----

コンテナがクラッシュしている場合、ログにその理由が表示されます。直前のクラッシュによるログを確認するには `--previous` を使用します。

Service を確認します：

[source,bash,role="execute"]
----
oc get svc -n app-management
----

Service には `ClusterIP` があります。これはクラスター内部からのみアクセス可能です。外部に公開するには、Route（ルート）が必要です。

TIP: コンソールの **Networking > Services**（プロジェクト: `app-management`）でも確認できます。`weathernow` をクリックして、Service の詳細、エンドポイント、およびバックエンドの Pod を確認してください。

== 公開とスケーリング（Expose & Scale）

=== Route の作成（Create a Route）

image::diagrams/02_route.png[OpenShift Route - Service - Pods, 500, align=center, link=self, window=blank]
Route は、OpenShift ルーター（HAProxy ベースの Ingress コントローラー）を介して外部 URL を Service に接続します。

[source,bash,role="execute"]
----
oc create route edge weathernow --service=weathernow
----

`edge` 終端は、TLS がルーターによって処理されることを意味します。ユーザーとルーター間のトラフィックは暗号化され、ルーターから Pod までは通常の HTTP になります。

Route を確認します：

[source,bash,role="execute"]
----
oc get route weathernow -n app-management
----

コンソールの **Workloads → Topology**（プロジェクト: `app-management`）に戻ります。アプリケーション上に Route のアイコンが表示されているのがわかります：

image::app-mgmt-deploy-topology.png[Topology view showing weathernow application with route, link=self, window=blank]
Route の URL をクリックして、ブラウザで WeatherNow アプリを開きます：

image::app-mgmt-weathernow-app.png[WeatherNow application showing weather data, link=self, window=blank]
これで、アプリケーションにクラスター外部からアクセスできるようになりました。

=== アプリケーションのスケーリング（Scale the Application）

本番環境において Pod が 1 つだけでは不十分です。3 つのレプリカにスケーリングします：

[source,bash,role="execute"]
----
oc scale deployment weathernow --replicas=3
----

**OCP Console** タブに切り替えます：**Workloads -> Pods**（プロジェクト: `app-management`）。新しい Pod が表示され、ステータスがリアルタイムで遷移する（Pending → ContainerCreating → Running）のを確認します。

TIP: **Workloads** メニューが表示されない場合は、左上のドロップダウンを使用して **Administrator** パースペクティブに切り替えてください。

image::app-mgmt-scaling-pods.png[Pod list showing 3 weathernow pods after scaling, link=self, window=blank]
CLI 経由でも確認できます：

[source,bash,role="execute"]
----
oc get pods -n app-management
----

3 つの Pod がすべて `Running` で表示されるはずです。Service は自動的にこれらすべてにトラフィックをロードバランシングします（設定は不要です）。Service は **label selectors**（ラベルセレクター）を使用して Pod を検出します：

[source,bash,role="execute"]
----
oc get endpointslice -l kubernetes.io/service-name=weathernow -n app-management
----

各 Pod の IP がエンドポイントとしてリストされます。新しい Pod が起動すると自動的に追加され、Pod が停止すると削除されます。

== 弾力性と自己修復（Resilience）

=== 自己修復（Self-Healing）

Pod が停止すると、OpenShift はそれを自動的に置換します。実際の動作を確認してみましょう。

まず、Pod を 1 つ削除します：

[source,bash,role="execute"]
----
oc delete pod $(oc get pods -n app-management -o jsonpath='{.items[0].metadata.name}') -n app-management --wait=false
----

すぐに Pod を確認して、自己修復の動作を観察します：

[source,bash,role="execute"]
----
oc get pods -n app-management
----

1 つの Pod が `Terminating` で、新しい Pod が `ContainerCreating` または `Running` になっているのが確認できるはずです。数秒後にもう一度実行します：

[source,bash,role="execute"]
----
sleep 5 && oc get pods -n app-management
----

合計が 3 つのレプリカに戻り、すべて `Running` になります。置換は手動の介入なしで数秒で行われました。

TIP: **OCP Console** の **Workloads -> Pods**（プロジェクト: `app-management`）でもこれを確認できます。コンソールには、色分けされたインジケーターで Pod のステータス遷移がリアルタイムで表示されます。

**Deployment コントローラー**が、実際の状態（2 つの Pod）と期待される状態（3 つの Pod）が一致していないことを検出し、代替を作成しました。これは手動の介在なしに数秒で実行されます。

=== アプリケーションプローブ（Application Probes）

OpenShift は、アプリケーションが実際に正常であるかどうかをどのように判断するのでしょうか？ プローブがない場合、内部のアプリがフリーズしたり、リスナーがクラッシュしたり、すべてのリクエストにエラーを返していたりしても、Pod は `Running` と表示されてしまいます。プローブがこの問題を解決します。

* **Readiness プローブ** - 「この Pod はトラフィックを処理できるか？」失敗した場合、Pod は Service のエンドポイントから削除されます。リクエストは送信されなくなります。
* **Liveness プローブ** - 「この Pod はまだ生きているか？」失敗した場合、OpenShift はコンテナを再起動します。

**意図的に障害を発生させる**

プローブが失敗したときに何が起こるか見てみましょう。**誤ったポート**（何もリッスンしていないポート 9999）を指す Readiness プローブを追加します：

[source,bash,role="execute"]
----
oc patch deployment weathernow -n app-management --type=json -p='[
  {"op":"add","path":"/spec/template/spec/containers/0/readinessProbe","value":{
    "tcpSocket":{"port":9999},
    "initialDelaySeconds":5,
    "periodSeconds":5
  }}
]'
----

NOTE: パッチにより新しいロールアウトがトリガーされます。ターミナルに Pod のステータスがストリーミング表示される場合は、**Ctrl+C** を押してプロンプトに戻してください。

ロールアウトを監視します。**これは失敗することが予期されています**。プローブが誤ったポートを指しているため、新しい Pod が準備完了（Ready）になることはありません：

[source,bash,role="execute"]
----
oc rollout status deployment/weathernow -n app-management --timeout=30s || true
----

30 秒後に `error: timed out waiting for the condition` と表示されるはずです。これが正しい結果です。Readiness プローブが失敗しているため、ロールアウトが停止しました。まだ実行中の場合は、**Ctrl+C** を押して終了し、続行してください。

Pod を確認します：

[source,bash,role="execute"]
----
oc get pods -n app-management
----

Pod が `0/1 Running` と表示されているはずです。コンテナは実行中ですが、Readiness プローブが失敗しているため、OpenShift はトラフィックを送信しません。**OCP Console** で、**Workloads -> Pods**（プロジェクト: `app-management`）に移動します：

image::broken-probe-pods.png[Pod list showing 0/1 Running pod with failed readiness probe, link=self, window=blank]
`0/1` の Pod をクリックし、**Events**（イベント）タブをクリックします。`Readiness probe failed: dial tcp ... connect: connection refused` というメッセージが繰り返し表示されているのが確認できます：

image::broken-probe-events.png[Events tab showing readiness probe failure messages, link=self, window=blank]
CLI でも確認します：

[source,bash,role="execute"]
----
oc describe pod -l deployment=weathernow -n app-management | grep -A2 "Readiness"
----

Pod は起動していますが、準備ができていません。トラフィックは到達しません。これは本番環境でアプリのヘルスエンドポイントがダウンしたときに起こることと同じです。OpenShift は問題のある Pod からユーザーを自動的に保護します。

**プローブの修正**

ここで修正します。Readiness プローブを httpd が実際にリッスンしているポート 8080 に向け、Liveness プローブも追加します：

[source,bash,role="execute"]
----
oc patch deployment weathernow -n app-management --type=json -p='[
  {"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe","value":{
    "tcpSocket":{"port":8080},
    "initialDelaySeconds":5,
    "periodSeconds":10
  }},
  {"op":"add","path":"/spec/template/spec/containers/0/livenessProbe","value":{
    "tcpSocket":{"port":8080},
    "initialDelaySeconds":15,
    "periodSeconds":20
  }}
]'
----

NOTE: パッチにより新しいロールアウトがトリガーされます。ターミナルに Pod のステータスがストリーミング表示される場合は、**Ctrl+C** を押してプロンプトに戻してください。

NOTE: プローブは複数のタイプをサポートしています：`httpGet`（HTTP エンドポイントをチェック）、`tcpSocket`（ポートがリッスンしているかチェック）、および `exec`（コンテナ内でコマンドを実行）。アプリに適合するものを選択してください。Web サービスでは `/healthz` エンドポイントに対する `httpGet` が最も一般的です。

ロールアウトが完了するのを待ちます：

[source,bash,role="execute"]
----
oc rollout status deployment/weathernow -n app-management --timeout=60s
----

NOTE: `deployment "weathernow" successfully rolled out` または `Completed` と表示されたら、**Ctrl+C** を押して終了し、続行してください。

[source,bash,role="execute"]
----
oc get pods -n app-management
----

すべての Pod が `1/1 Running` と表示され、プローブが通過してトラフィックが流れるようになります。これで、本番の OpenShift クラスターで最も一般的な問題の 1 つである Readiness プローブの失敗を診断し、修正することができました。

TIP: **OCP Console** で **Workloads -> Deployments** に移動し、`weathernow` Deployment の 3 点リーダーメニューをクリックして、**Edit Health Checks**（ヘルスチェックの編集）を選択します：

image::deployment-actions-menu.png[Deployment actions menu showing Edit Health Checks option, link=self, window=blank]
このフォームは、Liveness、Readiness、および Startup プローブの違いを視覚的に示しており、JSON パッチを記述することなく設定できます：

image::edit-health-checks.png[Edit Health Checks form showing configured readiness and liveness probes, link=self, window=blank]
=== 不正なデプロイのロールバック（Rollback a Bad Deployment）

誰かが不具合のあるイメージの更新をプッシュしてしまいました。どのように元に戻しますか？

イメージを変更して、不具合のあるデプロイをシミュレートします：

[source,bash,role="execute"]
----
oc set image deployment/weathernow weathernow=registry.access.redhat.com/ubi9/nginx-124 -n app-management
----

NOTE: ターミナルに Pod のステータスがストリーミング表示される場合は、**Ctrl+C** を押してプロンプトに戻してください。

ロールアウトの履歴を確認します。OpenShift はすべての変更を記録しています：

[source,bash,role="execute"]
----
oc rollout history deployment/weathernow -n app-management
----

複数のリビジョンが表示されます。Deployment を変更するたびに、新しいリビジョンが作成されます。

コンソールでもこれを視覚的に確認できます。**Workloads -> Deployments -> weathernow** に移動し、**ReplicaSets** タブをクリックします：

image::app-mgmt-replicasets-history.png[ReplicaSets tab showing deployment revision history with active and scaled-down replicas, link=self, window=blank]
各 ReplicaSet はリビジョンを表します。アクティブなものは `1 of 1 pods` と表示され、以前のリビジョンは `0 of 0 pods` にスケーリングされます。OpenShift は即座にロールバックできるようにこれらを保持しています。

以前の正常に動作していたバージョンにロールバックします：

[source,bash,role="execute"]
----
oc rollout undo deployment/weathernow -n app-management
----

NOTE: ターミナルに Pod のステータスがストリーミング表示される場合は、**Ctrl+C** を押してプロンプトに戻してください。

元のイメージが復元されたことを確認します：

[source,bash,role="execute"]
----
oc get deployment weathernow -n app-management -o jsonpath='{.spec.template.spec.containers[0].image}'
----

元の WeatherNow イメージが表示されるはずです（OpenShift は ImageStream を介してイメージタグを解決するため、ダイジェストとして表示されます）：

----
quay.io/openshift-workshop-applications/weathernow@sha256:362b6db3...
----

[source,bash,role="execute"]
----
oc rollout status deployment/weathernow -n app-management --timeout=60s
----

NOTE: これには 1 分程度かかる場合があります。5 分以上実行されている場合のみ **Ctrl+C** を押してください。

Deployment は動作するバージョンに戻りました。本番環境において、`oc rollout undo` は不具合のあるリリースから復旧するための最も迅速な方法となることが多く、コードを修正して再デプロイするよりも高速です。

== PodDisruptionBudget（PDB）

PodDisruptionBudget (PDB) は、OpenShift に対して _「メンテナンス中であっても、常に最低 N 個の Pod を実行し続けること」_ を指示します。アップグレードや修理のためにノードをドレイン（Evict/排他）するとき、Eviction API は Pod を削除する前に PDB をチェックします。Pod を削除することで最小数を下回る場合、安全になるまでドレインがブロックされます。

誤って設定された PDB はクラスターアップグレード停止の最大の原因（#1 cause）であるため、これは重要です。アップグレードプロセスはノードを 1 つずつドレインしますが、不適切な PDB が 1 つでもあるとアップグレード全体が期限なくブロックされる可能性があります。

=== PDB の作成（Create a PDB）

weathernow のデプロイは 3 つのレプリカを実行しています。常に最低 2 つの Pod が利用可能な状態を維持するように要求する PDB を作成します：

[source,bash,role="execute"]
----
cat <<'EOF' | oc apply -f -
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: weathernow
  namespace: app-management
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: weathernow
EOF
----

PDB を確認します：

[source,bash,role="execute"]
----
oc get pdb weathernow -n app-management
----

次のように表示されるはずです：

----
NAME         MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
weathernow   2               N/A               1                     5s
----

`ALLOWED DISRUPTIONS: 1` は、現在 1 つの Pod を安全に排除できることを意味します（3 実行中 - 最小 2 = 1 予備）。

=== PDB の動作確認（See the PDB in Action）

Pod を削除し、PDB カウンターを監視します：

[source,bash,role="execute"]
----
oc delete pod $(oc get pods -n app-management -l app=weathernow -o jsonpath='{.items[0].metadata.name}') -n app-management
----

[source,bash,role="execute"]
----
oc get pdb weathernow -n app-management
----

代替 Pod が起動する間、`ALLOWED DISRUPTIONS` は一時的に `0` に下がります。数秒待ってから再度確認します：

[source,bash,role="execute"]
----
sleep 10 && oc get pdb weathernow -n app-management
----

`1` に戻りました。代替 Pod が準備完了になり、バジェットに再び余裕ができました。

=== 障害の再現: ノードドレインのブロック（Break It: Block a Node Drain）

本番環境で最もよくある PDB の問題（`minAvailable` をレプリカ数と等しく設定すること）をシミュレートします。これは _「すべての Pod が常に実行されていなければならない」_ ことを意味し、安全に聞こえますがメンテナンスが不可能になります。

[source,bash,role="execute"]
----
oc patch pdb weathernow -n app-management --type=merge -p '{"spec":{"minAvailable":3}}'
----

[source,bash,role="execute"]
----
oc get pdb weathernow -n app-management
----

`ALLOWED DISRUPTIONS: 0` - どの Pod も排除できません。クラスターアップグレード中に発生することをシミュレートして、ノードのドレインを試みます：

[source,bash,role="execute"]
----
NODE=$(oc get pod -n app-management -l app=weathernow -o jsonpath='{.items[0].spec.nodeName}')
echo "Draining node: $NODE"
oc adm drain $NODE --pod-selector=app=weathernow --delete-emptydir-data --ignore-daemonsets --timeout=10s 2>&1 || true
echo "---"
echo "Uncordoning node..."
oc adm uncordon $NODE
----

ドレインは失敗します：

----
Cannot evict pod as it would violate the pod's disruption budget.
----

これがまさにクラスターアップグレードをブロックする原因です。OpenShift アップグレードコントローラーは各ノードをドレインしようとしますが、この PDB に阻まれ、永久に待機します。コマンドは最後に自動的にノードの Uncordon（スケジューリングの再開）を行うため、スケジューリングが復元されます。

=== PDB の修正（Fix the PDB）

`minAvailable` を 2 に戻します。これにより、メンテナンス中に一度に 1 つの Pod を排除できるようになります：

[source,bash,role="execute"]
----
oc patch pdb weathernow -n app-management --type=merge -p '{"spec":{"minAvailable":2}}'
----

[source,bash,role="execute"]
----
oc get pdb weathernow -n app-management
----

`ALLOWED DISRUPTIONS: 1` - ノードのドレインが再び機能するようになります。

**まとめ:** クラスターのアップグレードが停止した場合は、`oc get pdb -A` を実行し、`ALLOWED DISRUPTIONS: 0` を探します。`minAvailable` がレプリカ数と等しい場合は、それを下げるか `maxUnavailable: 1` に切り替えます。すべての排除をブロックする PDB はアプリを保護するのではなく、クラスター全体のメンテナンスをブロックしてしまいます。

== クリーンアップとまとめ（Cleanup & Summary）

=== まとめ（Summary）

OpenShift におけるアプリケーションライフサイクルのコアプロセスを完了しました：

* **デプロイ（Deploy）** - `oc new-app` は 1 つのコマンドで Deployment と Service を作成します
* **検査（Inspect）** - 診断のための `oc describe pod` および `oc logs`
* **公開（Expose）** - `oc create route edge` は TLS 終端された外部アクセスを追加します
* **スケーリング（Scale）** - `oc scale` でレプリカ数を調整し、Service が自動ロードバランシングを行います
* **自己修復（Self-heal）** - Pod を削除すると、OpenShift は数秒でそれを置換します
* **ヘルスチェック（Health checks）** - プローブにより、正常な Pod のみがトラフィックを受信するようにします
* **ロールバック（Rollback）** - `oc rollout undo` は不具合のあるデプロイを即座に元に戻します
* **PDB** - `minAvailable` はドレイン中の可用性を保護します。設定ミスのある PDB はアップグレードをブロックします

**主要コマンド:**

[source,bash]
----
oc new-app --name=myapp --image=myimage       # デプロイ
oc describe pod <pod-name>                     # 検査
oc logs <pod-name>                             # ログの確認
oc create route edge myapp --service=myapp     # TLSによる公開
oc scale deployment myapp --replicas=N         # スケーリング
oc rollout undo deployment/myapp               # ロールバック
oc get pdb -A                                  # 障害バジェットの確認
----

=== クリーンアップ（Cleanup）

[source,bash,role="execute"]
----
oc delete namespace app-management --ignore-not-found
echo "Cleanup complete"
----

NOTE: これにより、返る前にネームスペースが完全に削除されるまで待機します。これにより、次のモジュールでクリーンに再作成できるようになります。
