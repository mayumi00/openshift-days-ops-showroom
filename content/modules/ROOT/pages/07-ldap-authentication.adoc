= アイデンティティとユーザー
:page-toclevels: 1

**所要時間:** 15〜20 分 +
**形式:** ハンズオンでのアイデンティティプロバイダー設定

include::partial$console-access.adoc[]

== シナリオ

お使いのクラスターは HTPasswd 管理者アカウントで動作しています。初期セットアップには問題ありませんが、本番環境には本物のアイデンティティ管理が必要です。このモジュールでは、LDAP ディレクトリを統合し、グループを OpenShift に同期し、異なるチームが異なるアクセス権を取得できるように RBAC を構成し、実際にユーザーとしてログインしてテストします。

OpenShift の OAuth サーバーは、LDAP、OpenID Connect、HTPasswd、GitHub、GitLab、Google など、複数のアイデンティティプロバイダーをサポートしています。ここでは、最も一般的なエンタープライズセットアップであり、グループ同期の実証に適しているため LDAP を使用します。OIDC モジュールでは、よりモダンな代替手段をカバーしています。

TIP: サポートされているアイデンティティプロバイダーの完全なリストについては、link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/authentication_and_authorization/understanding-identity-provider[アイデンティティプロバイダーの理解, window=blank] を参照してください。

== LDAP の設定

=== ステップ 1: デフォルト認証の確認

現在の OAuth 設定を確認します：

[source,bash,role="execute"]
----
oc get oauth cluster -o yaml
----

TIP: コンソールの **Administration > Cluster Settings > Configuration > OAuth** でも確認できます。設定されているアイデンティティプロバイダーが読みやすい形式で表示されます。

`spec.identityProviders` セクションを確認します。`htpasswd` アイデンティティプロバイダーがすでに設定されていることがわかります。これは、現在使用している `admin` アカウントを提供するために、クラスターのプロビジョニング中にセットアップされたものです。

[NOTE]
====
新規作成直後のクラスターでは、`spec` は空（`spec: {}`）です。このワークショップクラスターには HTPasswd が事前設定されています。以下の OAuth 設定には、既存の HTPasswd プロバイダーと新しい LDAP プロバイダーの両方が含まれており、両方が同時に機能します。
====

**`kubeadmin` について**

作成直後の OpenShift クラスターには、`kube-system` 内に Secret として保存された `kubeadmin` ブートストラップアカウントが用意されています。このアカウントはアイデンティティプロバイダーを完全にバイパスします。これは初期セットアップのみを目的としたものです。このワークショップクラスターでは、`kubeadmin` はすでに削除されており、現在使用している `admin` HTPasswd アカウントに置き換えられています。これが適切な本番環境の姿勢です。

削除されていることを確認できます：

[source,bash,role="execute"]
----
oc get secret -n kube-system kubeadmin -o yaml
----

期待される結果：`not found` - ブートストラップアカウントが削除されていることを確認します。

=== ステップ 2: LDAP 構造の理解

このラボ環境では、以下のグループを持つ LDAP が提供されています：

* **ose-user**: OpenShift アクセス権を持つユーザー（すべてのユーザーはこのグループに属する必要があります）
* **ose-normal-dev**: 一般開発者（normaluser1、teamuser1、teamuser2）
* **ose-fancy-dev**: 上級権限を持つシニア開発者（fancyuser1、fancyuser2）
* **ose-teamed-app**: プロジェクトコラボレーションチーム（teamuser1、teamuser2）

**LDAP ユーザー認証情報:** すべてのユーザーのパスワードは `Op#nSh1ft` です。

=== ステップ 3: LDAP アイデンティティプロバイダーの設定

LDAP 認証を設定するには、以下が必要です：

1. LDAP バインドパスワードを含む **Secret**
2. LDAP サーバーの CA 証明書を含む **ConfigMap**
3. LDAP アイデンティティプロバイダーを定義する **OAuth 設定**

**LDAP バインドパスワードの Secret を作成します：**

[source,bash,role="execute"]
----
oc create secret generic ldap-secret \
  --from-literal=bindPassword='b1ndP^ssword' \
  -n openshift-config
----

**LDAP サーバーから CA 証明書チェーンを抽出します：**

[source,bash,role="execute"]
----
mkdir -p $HOME/support
echo | openssl s_client -connect ldap.jumpcloud.com:636 -showcerts 2>/dev/null | awk 'BEGIN{n=0} /BEGIN CERTIFICATE/{n++} n>=2{print}' > $HOME/support/ca.crt
----

NOTE: これにより、LDAP サーバーの TLS ハンドシェイクから直接中間 CA 証明書およびルート CA 証明書を抽出します。これは、サーバーの現在の証明書チェーンと一致しない可能性がある静的な CA ファイルをダウンロードするよりも信頼性が高くなります。

**CA 証明書を使用して ConfigMap を作成します：**

[source,bash,role="execute"]
----
oc create configmap ca-config-map \
  --from-file=ca.crt=$HOME/support/ca.crt \
  -n openshift-config
----

**OAuth 設定を作成して適用します：**

[source,bash,role="execute"]
----
bash <(curl -sL https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/07-ldap-authentication/configure-oauth-ldap.sh)
----

このスクリプトは、既存の HTPasswd プロバイダーとともに LDAP アイデンティティプロバイダーを追加する OAuth 設定を作成します。設定内容：バインド DN（`uid=openshiftworkshop,...`）、ログインを `ose-user` グループに限定する `memberOf` フィルター付き LDAP URL（`ldaps://ldap.jumpcloud.com`）、属性マッピング（`dn` -> ID、`mail` -> メールアドレス、`cn` -> 表示名、`uid` -> ユーザー名）、および上記で作成した CA 証明書とバインドパスワードを参照します。

**OAuth 設定の理解**

`oauth-cluster.yaml` ファイルは LDAP アイデンティティプロバイダーを設定します。主な要素：

**主要パラメーター：**

* **name**: このアイデンティティプロバイダーのユニーク識別子（複数持つことが可能）
* **mappingMethod: claim**: ユーザー名のアサイン方法（最初のアイデンティティプロバイダーが優先される）
* **attributes**: LDAP フィールドを OpenShift ユーザー属性にマッピング
* **bindDN/bindPassword**: LDAP 検索用の認証情報
* **ca**: LDAP サーバー SSL を検証する証明書
* **url**: LDAP サーバーの位置および検索フィルター

詳細な LDAP 設定については、link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/authentication_and_authorization/configuring-ldap-identity-provider[LDAP アイデンティティプロバイダーの設定, window=blank] を参照してください。

**OAuth オペレーターの展開状況を監視します：**

[source,bash,role="execute"]
----
oc rollout status deployment/oauth-openshift -n openshift-authentication --timeout=120s
----

NOTE: 完了までに 1〜2 分かかる場合があります。5 分以上実行されている場合のみ **Ctrl+C** を押し、コマンドを再実行してください。

待機対象: `deployment "oauth-openshift" successfully rolled out`

**OAuth Pod が実行中であることを確認します：**

[source,bash,role="execute"]
----
oc get pods -n openshift-authentication
----

すべての oauth-openshift Pod が `Running` および `Ready 1/1` である必要があります。

OAuth Pod は展開後に LDAP 接続を完全に初期化するまで少し時間が必要です。次に進む前に、LDAP ログインが実際に機能することを確認します：

[source,bash,role="execute",subs="attributes"]
----
OCP_SERVER=$(oc whoami --show-server)
echo "Waiting for LDAP authentication to be ready..."
ELAPSED=0
until oc login -u normaluser1 -p 'Op#nSh1ft' $OCP_SERVER --insecure-skip-tls-verify 2>&1 | grep -q "Login successful"; do
  sleep 10; ELAPSED=$((ELAPSED+10))
  [ $ELAPSED -ge 300 ] && echo "ERROR: Timed out - LDAP may not be configured correctly" && break
done
oc login -u {openshift_cluster_admin_username} -p {openshift_cluster_admin_password} $OCP_SERVER --insecure-skip-tls-verify 2>/dev/null
echo "LDAP authentication is ready"
----

NOTE: 完了までに 1〜2 分かかる場合があります。5 分以上実行されている場合のみ **Ctrl+C** を押し、コマンドを再実行してください。

=== ステップ 5: LDAP グループの OpenShift への同期

LDAP グループの同期は、LDAP グループを OpenShift グループとしてインポートし、RBAC 管理を容易にします。

**グループ同期設定を作成します：**

[source,bash,role="execute"]
----
cat <<EOF > $HOME/support/groupsync.yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ldap.jumpcloud.com
bindDN: uid=openshiftworkshop,ou=Users,o=5e615ba46b812e7da02e93b5,dc=jumpcloud,dc=com
bindPassword: b1ndP^ssword
rfc2307:
  groupsQuery:
    baseDN: ou=Users,o=5e615ba46b812e7da02e93b5,dc=jumpcloud,dc=com
    derefAliases: never
    filter: '(|(cn=ose-*))'
  groupUIDAttribute: dn
  groupNameAttributes:
  - cn
  groupMembershipAttributes:
  - member
  usersQuery:
    baseDN: ou=Users,o=5e615ba46b812e7da02e93b5,dc=jumpcloud,dc=com
    derefAliases: never
  userUIDAttribute: dn
  userNameAttributes:
  - uid
EOF
----

この設定は、`ose-*` に一致する LDAP グループを検索し、一致する OpenShift グループを作成し、LDAP からメンバーシップを登録します。

**グループ同期を実行します：**

[source,bash,role="execute"]
----
oc adm groups sync --sync-config=$HOME/support/groupsync.yaml --confirm
----

出力に作成されたグループが表示されます：

----
group/ose-fancy-dev
group/ose-user
group/ose-normal-dev
group/ose-teamed-app
----

**同期されたグループを表示します：**

[source,bash,role="execute"]
----
oc get groups
----

以下のように表示されます：

----
NAME             USERS
ose-fancy-dev    fancyuser1, fancyuser2
ose-normal-dev   normaluser1, teamuser1, teamuser2
ose-teamed-app   teamuser1, teamuser2
ose-user         fancyuser1, fancyuser2, normaluser1, teamuser1, teamuser2
----

**特定のグループを検査します：**

[source,bash,role="execute"]
----
oc get group ose-fancy-dev -o yaml
----

グループに含まれるもの：

* LDAP メタデータ（同期時間、LDAP DN、LDAP サーバー）
* グループ内のユーザーリスト

**コンソールでも確認してみましょう:** **OCP Console** の **User Management -> Groups** に移動します：

image::ldap-groups-console.png[User Management Groups showing synced LDAP groups with member counts, link=self, window=blank]
`ose-fancy-dev` をクリックすると、fancyuser1 と fancyuser2 がメンバーとしてリストされているのがわかります。次に、**User Management -> Users** をクリックします：

image::ldap-users-console.png[User Management Users showing only users who have logged in, link=self, window=blank]
`normaluser1`（および `admin`）のみが表示されていることに注目してください。他のユーザーは LDAP グループ内に存在しますが、まだログインしていないため、OpenShift はユーザーオブジェクトを作成していません。

これは重要な違いです。**グループメンバーシップは即座に同期されます**が、**ユーザーオブジェクトは初回ログイン時に作成されます**。本番環境では、グループに 50 人のメンバーがいても、ユーザーオブジェクトは 10 個しか存在しないという場合があります。これは単に 40 人がまだログインしていないことを意味します。

[source,bash,role="execute"]
----
oc get users
----

CLI からも同じことが確認できます。認証されたことのあるユーザーのみがここに表示されます。

=== ステップ 6: グループを使用した RBAC の設定

`ose-fancy-dev` グループに **cluster-reader** 権限を付与し、クラスター全体のリソースを参照できるようにします：

[source,bash,role="execute"]
----
oc adm policy add-cluster-role-to-group cluster-reader ose-fancy-dev
----

**cluster-reader とは？** 編集権限なしで管理情報（すべてのプロジェクト、ノード、クラスター設定）の参照を許可するロールです。

コンソールで確認できます。**User Management -> RoleBindings** に移動し、Kind フィルターを **Cluster-wide RoleBindings** に切り替えて、`cluster-reader` を検索します：

image::ldap-clusterrolebinding-reader.png[Cluster-wide RoleBindings showing ose-fancy-dev group bound to cluster-reader, link=self, window=blank]
最初の行に、すべてのネームスペースにわたって `ose-fancy-dev` が `cluster-reader` にバインドされているのが見えます。まさに今設定した内容です。

ロールの詳細については、link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/authentication_and_authorization/using-rbac[RBAC を使用した権限の定義と適用, window=blank] を参照してください。

**一般ユーザーとしてテスト：**

[source,bash,role="execute"]
----
oc login -u normaluser1 -p 'Op#nSh1ft' $OCP_SERVER --insecure-skip-tls-verify
oc whoami
----

IMPORTANT: `oc whoami` が `normaluser1` と表示することを確認してください。依然として `admin` と表示される場合は、ログインに失敗しています。30 秒待ってから再試行してください。

[source,bash,role="execute"]
----
oc get projects
----

`app-` プロジェクトは表示されないはずです。normaluser1 はどのプロジェクト固有のグループにも属していません。すべての認証済みユーザーにアクセスを許可する 1 つまたは 2 つのシステムネームスペースが表示される場合がありますが、これは正常です。

**fancy developerとしてテスト：**

[source,bash,role="execute"]
----
oc login -u fancyuser1 -p 'Op#nSh1ft' $OCP_SERVER --insecure-skip-tls-verify
oc whoami
oc get projects
----

クラスター内の**すべてのプロジェクト**が表示されるようになります：

----
NAME                                     STATUS
default                                  Active
kube-system                              Active
openshift-authentication                 Active
openshift-monitoring                     Active
...
----

これにより、グループベースの RBAC が正しく動作していることが証明されました。

**現在のユーザーを確認：**

[source,bash,role="execute"]
----
oc whoami
oc whoami --show-context
----

=== ステップ 8: プロジェクトへのグループのマッピング

----

両方とも `yes` を返します（view ロールは読み取り操作を許可します）。

**完璧です！** これにより、運用チームがテストリソースを作成することなく RBAC が正しく設定されていることを検証できることが実証されました。

== セキュリティのベストプラクティス

**アイデンティティプロバイダーの構成後は、kubeadmin が削除されていることを確認してください**

[source,bash,role="execute",subs="attributes"]
----
oc login -u {openshift_cluster_admin_username} -p {openshift_cluster_admin_password} --insecure-skip-tls-verify
----

まず、実際のユーザーに cluster-admin を付与します：

[source,bash,role="execute"]
----
oc adm policy add-cluster-role-to-user cluster-admin fancyuser1
----

機能することを確認します：

[source,bash,role="execute"]
----
oc login -u fancyuser1 -p 'Op#nSh1ft' $OCP_SERVER --insecure-skip-tls-verify
oc auth can-i '*' '*'
----

出力: `yes`

**本番環境では、常に kubeadmin を削除してください：**

アイデンティティプロバイダーが動作することを確認し、少なくとも 1 人の LDAP/OIDC ユーザーに cluster-admin を付与した後、`kube-system` ネームスペースから kubeadmin Secret を削除します。これによりブートストラップアカウントが排除され、すべてのクラスターアクセスがエンタープライズアイデンティティプロバイダーを経由するようになります。このワークショップクラスターでは、kubeadmin はすでに削除されており、代わりに `admin` HTPasswd アカウントを使用しています。

**CronJob による LDAP グループ同期の自動化：**

グループ同期を手動で実行する代わりに、本番環境では通常、同期操作を自動的に実行する Kubernetes CronJob（たとえば 1 時間ごとなど）を作成します。これにより、手動の介入なしで LDAP グループメンバーシップの変更が OpenShift に反映されるようになります。

CronJob の動作内容：

* 定期的なスケジュールでの実行（例：1 時間ごとの場合は `*/60 * * * *`）
* 適切な権限を持つサービスアカウントの使用
* ConfigMap からのグループ同期設定のマウント
* `--confirm` フラグを指定した `oc adm groups sync` の実行

完全な実装の詳細については、link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/authentication_and_authorization/ldap-syncing#ldap-syncing-running-all-ldap-sync_configuring-ldap-syncing[LDAP 同期の自動化に関する公式ドキュメント, window=blank] を参照してください。

**このラボでは、学習目的のため手動グループ同期で十分です。**

== クリーンアップとまとめ

=== まとめ

LDAP 認証をエンドツーエンドで設定しました。外部ディレクトリへの接続、グループの同期、それらのグループのプロジェクトレベル RBAC へのマッピング、およびアクセスレベルの異なる 3 人の異なるユーザーとしてログインすることによる検証を行いました。

**本番環境での推奨事項：**

1. HTPasswd ではなく、LDAP/OIDC を使用する
2. 実際のアイデンティティプロバイダーを設定した後は kubeadmin を削除する
3. CronJob でグループ同期を自動化する
4. 個別のユーザーではなく、グループを RBAC に使用する
5. 最小権限の原則に従う：edit より view、admin より edit
