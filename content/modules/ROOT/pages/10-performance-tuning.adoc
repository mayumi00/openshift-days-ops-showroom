= パフォーマンストゥーニング
:page-toclevels: 1

== はじめに

=== モジュールの概要

**所要時間:** 15〜20 分 +
**対象者:** プラットフォームエンジニア、SRE、運用チーム

include::partial$console-access.adoc[]

**課題:** アプリケーションでパフォーマンス上の問題（リソース枯渇による Pod のクラッシュ、高負荷時の応答時間の遅延、不明確な容量計画など）が発生しています。

**このモジュールでの取り組み:** OpenShift のオートスケーリングおよびモニタリングツールを使用して、実際のパフォーマンス問題を診断して修正します。

=== 学習目標

* リソース関連の Pod 障害を診断して修正する
* Vertical Pod Autoscaler (VPA) を使用してアプリケーションリソースを適正規模（ライトサイジング）化する
* 変動する負荷に対応するために Horizontal Pod Autoscaler (HPA) を設定する
* 組み込みツールを使用してパフォーマンスを監視する

== パート 1: 過剰にプロビジョニングされたアプリケーション

開発者が「念のため」2Gi のメモリを要求するアプリケーションをデプロイしました。しかし、それは本当に必要なのでしょうか？

=== アプリのデプロイ

[source,bash,role="execute"]
----
oc new-project performance-demo
----

[source,bash,role="execute"]
----
oc apply -f https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/memory-hog.yaml
----

実行状態になるまで待ちます：

[source,bash,role="execute"]
----
oc get pods -w
----

Pod が `Running` と表示されたら `Ctrl+C` を押します。

=== 要求されたリソースの確認

[source,bash,role="execute"]
----
oc get deployment memory-hog -o jsonpath='{.spec.template.spec.containers[0].resources}' | jq .
----

このアプリは **2Gi のメモリ**と **500m の CPU** を要求しました。1 つの Pod に対してリザーブされているクラスター容量としてはかなりの大きさです。

=== 実際の使用量の確認

TIP: 前のモジュールで別のユーザーとしてログインしていた場合は、管理者としてログインし直してください。コンソール: ユーザー名 `{openshift_cluster_admin_username}` / パスワード `{openshift_cluster_admin_password}`。認証エラーが表示された場合は、コンソールタブを再読み込みして再試行してください。

メトリクスが利用可能になるまで待ちます（Pod が起動してから約 60 秒）。待機している間に **OCP Console** タブに切り替え、**Workloads -> Pods**（プロジェクト: `performance-demo`）に移動します。Pod 名をクリックして **Metrics**（メトリクス）タブを確認すると、メモリ使用量がリアルタイムで反映されるのを確認できます。このアプリは CPU をほとんど使用しないため、CPU はゼロ近くになります。

image::perf-pod-metrics.png[Pod Metrics tab showing CPU and memory usage graphs, link=self, window=blank]
[source,bash,role="execute"]
----
echo "Waiting 60s for metrics to populate..."
sleep 60
oc adm top pod -l app=memory-hog
----

アプリが実際に使用しているメモリは、リザーブした 2Gi よりもはるかに少なく、正確な数値は変動しますが、通常は 200Mi を大きく下回ります。これは、他の Pod が使用できない **1.8Gi 以上の無駄な容量**が存在することを意味します！

== パート 2: VPA によるライトサイジング

Vertical Pod Autoscaler (VPA) は実際の使用量を分析し、適切なリソース値を推奨（レコメンド）します。

=== VPA のインストール（必要な場合）

VPA がインストールされているか確認します：

[source,bash,role="execute"]
----
oc get pods -n openshift-vertical-pod-autoscaler
----

インストールされていない場合：

[source,bash,role="execute"]
----
oc apply -f https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/vpa-operator.yaml
----

オペレーターの準備ができるまで待ちます（約 1 分）：

[source,bash,role="execute"]
----
echo "Waiting for VPA operator..."
ELAPSED=0
until oc get csv -n openshift-vertical-pod-autoscaler 2>/dev/null | grep -q Succeeded; do
  sleep 10; ELAPSED=$((ELAPSED+10))
  [ $ELAPSED -ge 180 ] && echo "ERROR: Timed out - check 'oc get csv -n openshift-vertical-pod-autoscaler'" && break
done
echo "Waiting for VPA CRD to register..."
until oc get crd verticalpodautoscalers.autoscaling.k8s.io 2>/dev/null; do
  sleep 5; ELAPSED=$((ELAPSED+5))
  [ $ELAPSED -ge 240 ] && echo "ERROR: Timed out waiting for CRD" && break
done
echo "VPA operator ready"
----

=== VPA レコメンデーションの取得

memory-hog Deployment をターゲットとする VPA リソースを作成します。ここでは `updateMode: "Off"` を使用しています。これは VPA が値を**推奨するのみ**で、Pod を自動的に変更しないことを意味します。本番環境では、まず `Off` から始めて推測値・推奨値を検証し、その後 `Auto` に切り替えて再起動時に VPA が Pod のサイズを自動変更するようにするのが一般的です。

[source,bash,role="execute"]
----
oc apply -f https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/vpa-memory-hog.yaml
----

VPA が Pod を分析して推奨事項を出力するまで待ちます：

[source,bash,role="execute"]
----
echo "Waiting for VPA recommendation..."
ELAPSED=0
until oc get vpa memory-hog-vpa -o jsonpath='{.status.recommendation}' 2>/dev/null | grep -q containerRecommendations; do
  sleep 10; ELAPSED=$((ELAPSED+10))
  [ $ELAPSED -ge 120 ] && echo "ERROR: Timed out - VPA may need more time, try running this block again" && break
done
oc get vpa memory-hog-vpa
----

以下のような出力が表示されるはずです：

----
NAME             MODE   CPU   MEM       PROVIDED   AGE
memory-hog-vpa   Off    35m   262144k   True       2m
----

詳細な推奨事項を表示します：

[source,bash,role="execute"]
----
oc get vpa memory-hog-vpa -o jsonpath='{.status.recommendation.containerRecommendations[0]}' | jq .
----

以下のような出力が表示されるはずです：

----
{
  "containerName": "memory-hog",
  "lowerBound": { "cpu": "25m", "memory": "262144k" },
  "target": { "cpu": "35m", "memory": "262144k" },
  "uncappedTarget": { "cpu": "35m", "memory": "262144k" },
  "upperBound": { "cpu": "500m", "memory": "512Mi" }
}
----

VPA は、要求された 2Gi ではなく **~256Mi のメモリ**を推奨しています。これは憶測ではなく、実際に観察された使用量に基づいています。

=== 適正規模化したリソースの適用

[source,bash,role="execute"]
----
oc patch deployment memory-hog --type=json -p='[
  {"op": "replace", "path": "/spec/template/spec/containers/0/resources/requests/memory", "value": "256Mi"},
  {"op": "replace", "path": "/spec/template/spec/containers/0/resources/limits/memory", "value": "512Mi"},
  {"op": "replace", "path": "/spec/template/spec/containers/0/resources/requests/cpu", "value": "50m"},
  {"op": "replace", "path": "/spec/template/spec/containers/0/resources/limits/cpu", "value": "200m"}
]'
----

=== 削減効果の検証

[source,bash,role="execute"]
----
oc get deployment memory-hog -o jsonpath='{.spec.template.spec.containers[0].resources}' | jq .
----

**結果:** 他のワークロードが使用できるように、**1.75Gi のメモリ**と **450m の CPU** を解放することができました。これを何百もの Pod に掛け合わせると、クラスターコストを大幅に削減できる可能性があります。

== パート 3: HPA による可変負荷への対応

image::diagrams/10_hpa.png[Horizontal Pod Autoscaler Flow, align=center, link=self, window=blank]
次に、トラフィックに基づいて水平スケーリングする必要があるアプリケーションをデプロイします。

=== スケーラブルなアプリケーションのデプロイ

[source,bash,role="execute"]
----
oc apply -f https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/demo-app.yaml
----

準備ができるまで待ちます：

[source,bash,role="execute"]
----
oc rollout status deployment/demo-app --timeout=120s
----

=== HPA の作成

CPU が 50% を超えたときに自動スケーリングするように設定します。なぜ 50% なのでしょうか？ターゲットを低くすると、Pod がより早くスケーリングします（応答性は高くなりますが、コストが高くなります）。ターゲットを高くすると、Pod がより密に配置されます（リソースを節約できますが、反応が遅くなります）。 50% は一般的な出発点です。アプリのレイテンシ要件に基づいてチューニングしてください。

[source,bash,role="execute"]
----
oc autoscale deployment demo-app --min=1 --max=5 --cpu-percent=50
----

HPA を確認します：

[source,bash,role="execute"]
----
oc get hpa demo-app
----

以下が表示されるはずです：

----
NAME       REFERENCE             TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
demo-app   Deployment/demo-app   cpu: <unknown>/50%   1         5         1          10s
----

`<unknown>` ターゲットは正常です。メトリクスサーバーが新しい Pod の CPU 使用率の報告を開始するまでに約 1 分かかります。

TIP: コンソールの **Workloads > HorizontalPodAutoscalers**（プロジェクト: `performance-demo`）で HPA を確認できます。現在の CPU パーセンテージとターゲットの比較、および現在のレプリカ数をリアルタイムで表示します。

=== 負荷の生成

2 番目のターミナルを開くか、以下をバックグラウンドで実行します：

[source,bash,role="execute"]
----
oc run load-generator --image=registry.access.redhat.com/ubi9/ubi-minimal --restart=Never -- /bin/sh -c "while true; do curl -s -o /dev/null http://demo-app:8080; done"
----

=== オートスケーリングの監視

負荷ジェネレーターが稼働している間、コンソールで **Workloads -> Pods**（プロジェクト: `performance-demo`）に移動し、HPA がスケールアップするにつれて新しい Pod が表示されるのを確認します。これが動作中のオートスケーラーです。

次に **Observe -> Dashboards** に移動し、**Kubernetes / Compute Resources / Namespace (Pods)** を選択してプロジェクト `performance-demo` を選択します。**CPU Quota** テーブルで負荷が複数の Pod に分散されているのが確認できます。各 demo-app Pod は ~40-50% の CPU を使用し、`load-generator` Pod が最も多くの CPU を消費しています。上部の **CPU Utilisation (from requests)** パーセンテージは、総使用量が単一の Pod に対して元々要求された量を超えているため、100% を大きく上回ります。

image::perf-hpa-pods-scaling.png[Pod list showing multiple demo-app pods after HPA scale-up, link=self, window=blank]
CLI からも監視できます：

[source,bash,role="execute"]
----
oc get hpa demo-app -w
----

`REPLICAS` カラムと `TARGETS` カラムを観察します。これを実行する頃には HPA がすでにスケールアップしている可能性があります。2〜4 個のレプリカが表示され、CPU が 50% 近くになっている場合、オートスケーラーはすでに応答しています。`Ctrl+C` を押して続行します。

Pod がスケールしたことを確認します：

[source,bash,role="execute"]
----
oc get pods -l app=demo-app
----

=== 負荷の停止

[source,bash,role="execute"]
----
oc delete pod load-generator
----

負荷が減少してから約 5 分後に、HPA はスケールダウンします。これはスケールダウンのデフォルトの `stabilizationWindowSeconds` であり、フラッピング（頻繁なスケールイン・アウトの繰り返し）を防止します。待つ必要はありません。本番環境ではスケールダウンが意図的に緩やかに行われることを理解しておいてください。

== パート 4: キャパシティの意思決定

VPA を使用して 1 つのアプリをライトサイジングし、HPA を使用して別のアプリを自動スケーリングしました。次に全体像を見てみましょう：

[source,bash,role="execute"]
----
oc adm top nodes
----

ノード全体のメモリの割合を確認します。**OCP Console** で **Observe -> Dashboards** に移動し、**Kubernetes / Compute Resources / Namespace (Pods)** を選択して、プロジェクト `performance-demo` を選択します：

image::hpa-scaling-dashboard.png[Dashboard showing CPU usage and pod count during HPA scaling event, link=self, window=blank]
グラフは、時間の経過に伴う HPA スケーリングイベントの様子を示しています。**CPU Quota** テーブルでは、負荷がどのように分散されたかを確認できます。各 demo-app Pod は、ほぼ同等の CPU 使用率でトラフィックの一部を処理し、load-generator が最も多くの CPU を消費しています。上部の **CPU Utilisation (from requests)** パーセンテージは、総リクエストに対するネームスペース総使用量を反映しており、負荷発生時には 100% を大きく超えて上昇します。

負荷ジェネレーターを削除した後、HPA が demo-app レプリカをスケールダウンし、CPU 使用率が低下するのを監視します。これがエンドツーエンドで動作するオートスケーリングです。

キャパシティレビューで「新しいノードが必要なのか、それともアプリが単に過剰プロビジョニングされているだけなのか？」という質問に答えるには、このように確認を行います。多くのクラスターでは、VPA を導入するだけで、新しいインフラストラクチャを購入しなくても済むほどの十分な容量を確保できます。

=== 主要なまとめ

[cols="1,2"]
|===
|ツール |使用するタイミング

|**VPA**
|実際の使用量に基づいてリソースを最適化する（推奨事項を確認するには、まず `Off` モードを使用する）

|**HPA**
|変動する負荷に対して Pod を水平スケーリングする（50〜70% の CPU ターゲットを設定する）

|**oc adm top**
|現在のリソース消費量を迅速に確認する

|**Observe → Dashboards**
|過去の傾向とキャパシティ計画の確認
|===

**基本パターン:** リソースを勘に頼らない → VPA を使用して測定する → 推奨事項を適用する → 負荷の変動には HPA を使用する
