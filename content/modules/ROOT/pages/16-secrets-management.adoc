**所要時間:** 25 分 +
**形式:** ハンズオンラボ +
**対象者:** プラットフォームエンジニア、セキュリティエンジニア、IT運用担当者

== 学習目標

このモジュールを完了すると、以下のことができるようになります。

* 公式の Helm チャートを使用して OpenShift 上に HashiCorp Vault をデプロイする
* Vault ポリシー、Kubernetes 認証、および KV シークレットを構成する
* Vault Agent Injector を介して Vault シークレットを消費する Pod をデプロイする
* External Secrets Operator をデプロイして Vault からシークレットを取得し、Kubernetes シークレットに注入する

== なぜ Kubernetes 上で Vault を使用するのか？

HashiCorp Vault は、シークレット、証明書、および暗号化キーへのアクセスを保存および仲介します。コンテナイメージ、Git リポジトリ、または長期間有効な Kubernetes の `Secret` オブジェクトに資格情報を埋め込む代わりに、Vault は専用のシークレットストアに機密データを保持し、要求に応じて短期間有効なアクセス権を発行します。公式の https://github.com/hashicorp/vault-helm[Vault Helm チャート] は Kubernetes または OpenShift に Vault をインストールし、オプションで Pod へのシークレット注入用に Vault Agent Injector をデプロイできます。インジェクターはアドミッション時に Pod の仕様を変更するため、アプリケーションが起動する前に、初期化コンテナ（init container）が Vault に対して認証を行い、ボリューム内にシークレットをレンダリングできます。

このラボでは、https://github.com/validatedpatterns/layered-zero-trust[Layered Zero Trust Validated Pattern]（Validated Patterns Framework 上に構築された Red Hat の参照アーキテクチャ）のレイヤー 1 機能をカバーしています。そのパターンはコンポーネントをレイヤーにスタックします。

* *Validated Patterns Framework* — OpenShift GitOps (Argo CD) と Validated Patterns Operator を使用してクラスターをブートストラップします。これより上のすべては Argo CD によってデプロイおよび調整されます。
* *レイヤー 0 — 基盤 (Foundations)* — TLS、コンプライアンススキャン、高度なクラスター管理、および実行時セキュリティ強制
* *レイヤー 1 — 機能セット (Feature Sets)* — ワークロードアイデンティティ (SPIFFE/SPIRE)、シークレット管理 (Vault + ESO)、およびユーザー認証 (Keycloak)。オプションでプライベートイメージレジストリ (Quay + NooBaa)
* *レイヤー 2 — マッピング (Mapping)* — デモアプリケーション (qtodo)、およびオプションでセキュアなサプライチェーンパイプライン (RHTAS、RHTPA、OpenShift Pipelines)

Vault はそのスタック内のシークレットストアです。また、標準的なシークレット参照を予期するワークロード用に、Vault データをネイティブの Kubernetes `Secret` オブジェクトに同期するための External Secrets Operator (ESO) も使用します。

[NOTE]
====
このラボでは Vault を**開発モード (dev mode)**（自動アンシール、ルートトークン `root`）で実行します。開発モードは学習専用です。Vault Pod が再起動するとデータは失われます。本番環境で開発モードを使用しないでください。
====

.手順
. バスティオン（踏み台サーバー）からリポジトリをクローンし、インストーラーを実行します。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
cd ~/
git clone https://github.com/rhpds/openshift-days-ops-showroom.git
cd openshift-days-ops-showroom/setup-scripts/vault-config-scripts
./install-vault.sh
----

スクリプトの動作:

* HashiCorp Helm リポジトリを追加し、チャート `hashicorp/vault` をインストールします
* OpenShift 統合と**開発モード**を有効にします
* Vault UI 用の OpenShift **Route** を作成します
* Pod へのシークレット注入用に **Vault Agent Injector** を有効にします

出力例:

----

== Vault の構成

このステップでは、Kubernetes クラスター内のシークレットを安全に管理およびアクセスできるように、Vault ポリシーと認証方法を構成します。この構成により、承認されたアプリケーションのみが Vault から機密データを取得できるようになります。

まず CLI を使用して Vault ポリシーと認証方法を構成し、UI を確認して構成を検証します。これは Vault Pod の内部から行います。

.手順
. Vault Pod に接続します。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc exec -it -n vault vault-0 -- /bin/sh
export VAULT_ADDR=http://127.0.0.1:8200
export VAULT_TOKEN=root
----

. Pod にシークレットの読み取りを許可するポリシーファイルを作成します。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
cat <<EOF > /home/vault/read-policy.hcl
path "secret*" {
  capabilities = ["read"]
}
EOF
----

. ポリシーを適用します。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
vault policy write read-policy /home/vault/read-policy.hcl
----
+
. 次に、Kubernetes 認証を有効にします。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
vault auth enable kubernetes
----
+
. サービスアカウントトークンを介して Vault が Kubernetes API サーバーと通信できるようにします。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
vault write auth/kubernetes/config \
  token_reviewer_jwt="$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" \
  kubernetes_host="https://kubernetes.default.svc:443" \
  kubernetes_ca_cert=@/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
----
+
. `secret/` に KV v2 シークレットエンジンを有効にします。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
vault secrets enable -path=secret kv-v2 2>/dev/null || true
----
+
. ポリシーを `vault` ネームスペースのサービスアカウント `vault-serviceaccount` にバインドするロール `vault-role` を作成します。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
AUD=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token | cut -d. -f2 | base64 -d 2>/dev/null | sed -n 's/.*"aud":\["\([^"]*\)".*/\1/p')
vault write auth/kubernetes/role/vault-role \
  bound_service_account_names=vault-serviceaccount \
  bound_service_account_namespaces=vault \
  policies=read-policy \
  ttl=1h \
  audience="${AUD}"
----
+
Vault 1.21 は、サービスアカウントトークンの `aud` クレームをロールの `audience` に対して検証します。上記のコマンドは、Vault Pod トークンからクラスターオーディエンス（OpenShift では通常 `https://kubernetes.default.svc`）を読み取ります。
+
. 構成が完了したら、Vault Pod のシェルを終了します。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
exit
----

.手順

+
[source,bash,subs="+macros,+attributes",role=execute]
----

export VAULT_ADDR=http://127.0.0.1:8200

+
. シークレットを作成して確認します。
+
[source,bash,subs="+macros,+attributes",role=execute]

== Kubernetes Pod からのシークレットへのアクセス

Vault が構成され、シークレットが保存されたので、サンプルアプリケーションを `vault` ネームスペースにデプロイします。**Vault Agent Injector** は Pod を変更して、Kubernetes 認証で認証を行い、`/vault/secrets/` にシークレットをレンダリングする初期化コンテナ（init container）を追加します。

デプロイメントでは、アノテーションを使用して `secret/login` と `secret/my-first-secret` を注入します。

* `vault.hashicorp.com/agent-inject: "true"` — この Pod に対する注入を有効にします
* `vault.hashicorp.com/role: "vault-role"` — 使用する Kubernetes 認証ロール
* `vault.hashicorp.com/agent-inject-secret-<name>` — 取得する Vault パス
* `vault.hashicorp.com/agent-inject-template-<name>` — ボリュームに書き込まれるフォーマット

.手順
. *Vault Secrets App*（注入されたシークレットを受信し、OpenShift Route で公開される Web アプリケーション）をデプロイします。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
cat <<'EOF' | oc apply -f -
---

  name: vault-secrets-app-html
  namespace: vault

    app: vault-secrets-app

== External Secrets Operator によるシークレットへのアクセス

最初のデプロイメントでは、**Vault Agent Injector** を使用してシークレットを `/vault/secrets/` の下のファイルとしてレンダリングしました。**External Secrets Operator (ESO)** は異なるパターンを提供します。Vault からシークレットを読み取り、ネイティブの Kubernetes `Secret` オブジェクトとして具体化します。その後、ワークロードは他の Kubernetes シークレットを使用するのと同じ方法で、`env`、`envFrom`、またはボリュームマウントを介してこれらのシークレットを消費します。

=== External Secrets Operator のインストール

.手順
. 公式の Helm チャートから `external-secrets` ネームスペースに ESO をインストールします。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
helm repo add external-secrets https://charts.external-secrets.io
helm repo update external-secrets
helm upgrade --install external-secrets external-secrets/external-secrets \
  -n external-secrets \
  --create-namespace \
  --set installCRDs=true \
  --wait --timeout 10m
----

. オペレーターが実行中であることを確認します。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get pods -n external-secrets
----

`external-secrets` のデプロイメント Pod が `Running` 状態になっているはずです。

=== Vault から同期するように ESO を構成する

ESO は、Vault UI で作成した `my-second-secret` を読み取り、それを `my-second-secret-sync` という名前の Kubernetes `Secret` に同期します。

開発モードでは、ESO は Kubernetes `Secret` に保存されているルートトークンを使用して Vault に対し認証を行います。`SecretStore` は Vault への到達方法を定義します。`ExternalSecret` はコピーする Vault パスとターゲットとなる Kubernetes `Secret` の名前を定義します。

.手順
. `vault` ネームスペースにトークン、`SecretStore`、および `ExternalSecret` を適用します。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
cat <<'EOF' | oc apply -f -
---
apiVersion: v1
kind: Secret
metadata:
  name: vault-token
  namespace: vault
type: Opaque
stringData:
  token: root
---
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: vault-backend
  namespace: vault
spec:
  provider:
    vault:
      server: "http://vault.vault.svc:8200"
      path: "secret"
      version: "v2"
      auth:
        tokenSecretRef:
          name: vault-token
          key: token
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: sync-my-second-secret
  namespace: vault
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: my-second-secret-sync
    creationPolicy: Owner
  data:
    - secretKey: username
      remoteRef:
        key: my-second-secret
        property: username
    - secretKey: password
      remoteRef:
        key: my-second-secret
        property: password
EOF
----

. ESO が Kubernetes `Secret` を作成したことを確認します。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get externalsecret,secretstore -n vault
oc get externalsecret sync-my-second-secret -n vault -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}{"\n"}'
oc get secret my-second-secret-sync -n vault -o jsonpath='{.data.username}{"\n"}' | base64 -d && echo
----

期待される結果: ExternalSecret の `Ready` ステータスが `True` であり、デコードされたユーザー名が `workshop-user-2` であること。


NOTE: ステータスが `SecretSyncedError` であり、`my-second-secret-sync` が作成されなかった場合は、Vault UI の `my-second-secret` に `username` と `password` の両方が含まれていることを確認し、エラーを検査してください。

[source,bash,subs="+macros,+attributes",role=execute]
----
oc describe externalsecret sync-my-second-secret -n vault | tail -20
oc get externalsecret sync-my-second-secret -n vault -w
----

`READY` が `True` になったら `Ctrl+C` を押し、上記の検証コマンドを再実行します。

=== 同期された Secret を使用する 2 番目のアプリケーションのデプロイ

Vault Agent ファイルからではなく、ESO が作成した Kubernetes `Secret` から資格情報を読み取る 2 番目のワークロードをデプロイします。

.手順
. アプリケーションをデプロイします。
+
[source,bash,subs="+macros,+attributes",role=execute]
----
cat <<'EOF' | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: eso-vault-test
  namespace: vault
  labels:
    app: eso-read-vault-secret
spec:
  replicas: 1
  selector:
    matchLabels:
      app: eso-read-vault-secret
  template:
    metadata:
      labels:
        app: eso-read-vault-secret
    spec:
      containers:
        - name: app
          image: registry.access.redhat.com/ubi9/ubi-minimal:latest
          command: ["sleep", "infinity"]
          env:
            - name: USERNAME
              valueFrom:
                secretKeyRef:
                  name: my-second-secret-sync
                  key: username
            - name: PASSWORD
              valueFrom:
                secretKeyRef:
                  name: my-second-secret-sync
                  key: password
EOF
----

+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get pods -n vault -l app=eso-read-vault-secret -w
----

Pod が `1/1` Ready になったら `Ctrl+C` を押します。

[start=2]
. Pod が同期された資格情報を受信したことを確認します。

[source,bash,subs="+macros,+attributes",role=execute]
----

完璧です！Vault Agent Injector からではなく、ESO が作成した Kubernetes `Secret` から資格情報を読み取る 2 番目のワークロードをデプロイしました。ESO はワークロード内でシークレットを消費するための代替手段であり、お好みのシークレットストアと組み合わせて使用できます。

== 学んだこと

* **OpenShift 上の Vault** は etcd の外部でシークレットを集中管理し、**Agent Injector** は実行時にそれらを Pod に渡します。
* **Kubernetes 認証** は、Vault アクセスをネームスペースおよびサービスアカウント（`vault-serviceaccount` → ロール `vault-role`）に紐付けます。
* **Vault Agent Injector** は、Pod 内部の `/vault/secrets/` の下のファイルにシークレットを書き込みます。
* **External Secrets Operator** は、`env`、`envFrom`、またはボリュームマウントで使用するために、Vault データをネイティブの Kubernetes `Secret` オブジェクトに同期します。
* 2 つの消費パターンをデプロイしました: Agent Injector (`vault-secrets-app`) と ESO バックの Kubernetes シークレット (`eso-vault-test`)。
