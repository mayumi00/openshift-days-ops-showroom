= OpenShift Virtualization
:page-toclevels: 1

**所要時間:** 20-25 分

include::partial$console-access.adoc[]

== シナリオ

データベース、ミドルウェア、Windows サービスなど、一部のワークロードはまだコンテナ化できません。OpenShift Virtualization を使用すると、KubeVirt（RHEL KVM 上に構築された CNCF プロジェクト）を使用して、同じプラットフォーム上でコンテナと並行してこれらの VM を実行できます。同じスケジューラー、同じネットワーク、同じモニタリング、同じ RBAC、同じ `oc` コマンドが使用可能です。

このモジュールでは、コンソールから VM を作成し、それが裏で実際には単なる Pod であることを確認し、ノード間でライブマイグレーションを行い、クローンを作成し、スナップショットを取得します。これらはすべて、コンテナに使用するのと同じツールで行います。

=== 事前条件の確認

OpenShift Virtualization はすでにインストールされている必要があります。確認します：

[source,bash,role="execute"]
----
oc get csv -n openshift-cnv | grep kubevirt
----

期待される出力（`Succeeded` と表示されます）：
----
kubevirt-hyperconverged-operator.v4.20.x   OpenShift Virtualization   4.20.x   Succeeded
----

== VM の作成と探索

=== VM の作成

まず、このモジュール用のプロジェクトを作成します：

[source,bash,role="execute"]
----
oc new-project vm-demo
----

次に、コンソールを使用して VM を作成します。これは、チームが AWS や Azure で体験するのと同じクラウドスタイルのエクスペリエンスです。

**ステップ 1: 作成ウィザードを開く**

. OpenShift コンソールで、左上のドロップダウンから **Fleet Virtualization** パースペクティブに切り替えます（ACM が有効化されていない場合は **Virtualization** という名前になります）
. **Create** ドロップダウンをクリックし、**From InstanceType** を選択します
+
image::virt-create-dropdown.png[Create VirtualMachine dropdown showing From InstanceType option, link=self, window=blank]
. 上部の **Project** ドロップダウンに `vm-demo` が表示されていることを確認します。表示されていない場合は検索して今すぐ選択します
+
image::virt-select-project.png[Project dropdown showing vm-demo search and selection, link=self, window=blank]
**ステップ 2: ブートソースと InstanceType の選択**

1. ウィザードの上部にあるボリュームリストから **Red Hat Enterprise Linux 9** ブートソースを選択します
2. **Select InstanceType** の下で、**Red Hat provided** -> **General Purpose** -> **medium: 1 CPUs, 4 GiB Memory** を選択します

OpenShift Virtualization は **InstanceTypes** を提供します。これは、クラウドインスタンスファミリーに類似した事前定義済みのコンピュートプロファイルです：

[cols="1,2"]
|===
|シリーズ |ユースケース

|**U** (Universal) |汎用ワークロード
|**O** (Overcommitted) |CPU オーバーコミットを伴う開発/テスト
|**CX** (Compute) |CPU 集中型ワークロード
|**M** (Memory) |メモリ集中型（データベース、キャッシュ）
|**N** (Network) |ネットワーク集中型ワークロード
|===

image::virt-create-wizard.png[VM creation wizard showing InstanceType selection and VM details, link=self, window=blank]
**ステップ 3: 構成と作成**

IMPORTANT: VM 名は正確に `rhel9-vm` と指定し、プロジェクトが `vm-demo` に設定されていることを確認してください。このモジュールの以降のコマンドではこれらの名前を使用するため、異なる値を使用すると失敗します。

**VirtualMachine details** セクションで：

1. **Name** を `rhel9-vm` に変更します
2. デフォルト設定のままにします：**30 GiB** ディスク、デフォルトのストレージクラス
3. **Start this VirtualMachine after creation** にチェックが入っていることを確認します
4. **Create VirtualMachine** をクリックします

VM の詳細ページが開きます。VM が起動するにつれて、ステータスが **Provisioning** から **Running** に変化するのが確認できます：

image::virt-provisioning.png[VM details page showing Provisioning status, link=self, window=blank]
**ステップ 4: VM コンソールへのアクセス**

VM が起動したら、**Console** タブをクリックします。VM の起動出力が表示された VNC コンソールが確認できます：

image::virt-vnc-boot.png[VNC console showing RHEL 9 boot output, link=self, window=blank]
**Open web console** をクリックして、新しいウィンドウで VM コンソールを開きます：

image::virt-open-web-console.png[Open web console link, link=self, window=blank]
**Guest login credentials** がコンソールの上部に表示されます。これらを使用してログインします：

image::virt-console-creds.png[VNC console with guest credentials shown at top, link=self, window=blank]
CLI 経由で認証情報を取得することもできます：

[source,bash,role="execute"]
----
DATA=$(oc get vm rhel9-vm -n vm-demo -o jsonpath='{.spec.template.spec.volumes[?(@.name=="cloudinitdisk")].cloudInitNoCloud.userData}')
echo "Username: $(echo "$DATA" | grep 'user:' | awk '{print $2}')"
echo "Password: $(echo "$DATA" | grep 'password:' | awk '{print $2}')"
----

サイズを選び、ブートイメージを選び、デプロイする。YAML は不要です。

=== それは単なる Pod です

これが運用チームにとって最も重要なポイントです。VM は `virt-launcher` Pod の内部で動作します。つまり、Pod の管理についてすでに知っているすべての知識が VM にも適用されます。同じスケジューラー、同じ RBAC、同じリソースクォータ、同じ `oc` コマンド。VM とコンテナで別々のツール、別々のチーム、別々のランブックを用意する必要はありません：

[source,bash,role="execute"]
----
oc get pods -n vm-demo
----

次のように表示されます：

----
NAME                          READY   STATUS    RESTARTS   AGE
virt-launcher-rhel9-vm-xxxxx   2/2     Running   0          3m
----

これがあなたの VM です。Pod なのです。同じ `oc` コマンドが機能します：

[source,bash,role="execute"]
----
oc describe pod -l vm.kubevirt.io/name=rhel9-vm -n vm-demo | tail -10
----

== モニタリングとネットワーク

=== 統合モニタリング

VM メトリクスは、コンテナと同じ Prometheus スタックに流れ込みます。すべてに対して 1 つのダッシュボードで対応できます。VM 用に個別のモニタリングツールを用意する必要はありません。

VM の詳細ページで、**Metrics** タブをクリックして以下を確認します：

* 時間経過に伴うメモリ使用量
* 時間経過に伴う CPU 使用率
* ストレージの総読み取り/書き込み
* ストレージ IOPS
* ストレージレイテンシ

image::virt-metrics-tab.png[VM Metrics tab showing Memory CPU and Storage graphs, link=self, window=blank]
または CLI からクエリを実行します。VM は任意の Pod と同様にリソースを消費します：

[source,bash,role="execute"]
----
oc adm top pods -n vm-demo
----

=== VM の公開（コンテナと同じネットワーク）

VM はコンテナと同じ SDN 上で Pod IP を取得します。同じ Service、同じ Route、同じ NetworkPolicy を使用します。VM とコンテナで単一のネットワークモデルを使用します：

[source,bash,role="execute"]
----
oc get vmi rhel9-vm -n vm-demo -o jsonpath='{.status.interfaces[0].ipAddress}' && echo ""
----

VM を指す Service を作成します：

[source,bash,role="execute"]
----
oc apply -f - <<EOF
apiVersion: v1
kind: Service
metadata:
  name: rhel9-vm-ssh
  namespace: vm-demo
spec:
  selector:
    vm.kubevirt.io/name: rhel9-vm
  ports:
  - port: 22
    targetPort: 22
EOF
----

[source,bash,role="execute"]
----
oc get svc rhel9-vm-ssh -n vm-demo
----

コンテナを公開するのと同じ方法で、Service 経由で VM に到達できるようになりました。同じラベルセレクター、同じ Service タイプ、同じネットワークモデルです。

Web アプリケーション（Apache、IIS、Tomcat）を実行している VM の場合、ポート 80/443 で Service を作成し、TLS エッジ終端を備えた Route を作成します。これはコンテナに使用するのとまったく同じワークフローです。マルチティアアプリケーションを移行する場合、MTV で VM を移行し、Service と Route で接続すれば、アプリケーションを変更することなく OpenShift 上で稼働させることができます。

== VM ライフサイクル

=== ライブマイグレーション

これは OpenShift Virtualization を本番環境に対応させるための機能です。ノードにパッチを適用したり、OS をアップグレードしたり、ハードウェアを交換したりする必要がある場合、ノードをドレイン（排他）します。コンテナは自動的に再スケジューリングされ、VM も自動的にライブマイグレーションされます。`oc adm drain` はその両方を処理します。メンテナンスウィンドウ中のダウンタイムはゼロです。

**ステップ 1: マイグレーションの準備**

ライブマイグレーションには、移行元ノードと移行先ノード間で互換性のある CPU 機能が必要です。ワークショップクラスターのプールには Intel と AMD のノードが混在している場合があります。CPU 命令セットに互換性がないため、VM は同じ CPU ベンダーのノード間でのみマイグレーションできます。このスクリプトは VM の CPU ベンダーを検出し、有効なマイグレーションターゲットが存在するように、2 台以上のノードがあるベンダーに固定します：

[source,bash,role="execute"]
----
bash <(curl -sL https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/11-virtualization/prepare-migration.sh)
----

NOTE: VM を別のノードに移動する必要がある場合、これには 1 分ほどかかる場合があります。続行する前に `Ready - Node:` の出力を待ってください。

NOTE: 本番環境では、クラスター内で均一な CPU ハードウェアを確保するか、VM の仕様で特定の CPU モデルを使用します。これは、KubeVirt/OpenShift Virtualization デプロイメントにおける一般的な運用上の考慮事項です。

**ステップ 2: 現在のノードの確認**

マイグレーション前に VM が存在するノードを確認します：

[source,bash,role="execute"]
----
oc get vmi rhel9-vm -n vm-demo -o jsonpath='Node: {.status.nodeName}' && echo ""
----

**ステップ 3: マイグレーションのトリガー**

. VM 詳細ページで、右上隅の **Actions** ドロップダウンをクリックします
. **Migration** の上にマウスカーソルを置いてサブメニューを展開します
. **Compute** を選択します。これにより、VM の実行状態（CPU/メモリ）が別のノードにマイグレーションされます
+
image::virt-actions-migrate.png[Actions dropdown showing Migration submenu with Compute and Storage options, link=self, window=blank]
. マイグレーションダイアログで、**Automatically selected Node** を選択したまま **Migrate VirtualMachine** をクリックします
+
image::virt-migrate-auto-node.png[Migration dialog with Automatically selected Node option, link=self, window=blank]
**ステップ 4: マイグレーションの観察**

ライブマイグレーションの進行中、VM ステータスは **Migrating** に変化します：

image::virt-migrating-status.png[VM details showing Migrating status, link=self, window=blank]
マイグレーションは迅速に完了します（通常 30 秒以内）。ステータスが **Running** に戻ったら、ノードが変更されたことを確認します：

[source,bash,role="execute"]
----
oc get vmi rhel9-vm -n vm-demo -o jsonpath='Node: {.status.nodeName}' && echo ""
----

VM は稼働状態を維持したまま移動しました。ダウンタイムはなく、再接続も不要です。

=== VM のクローン

テスト、開発環境、またはスケールアウトのために VM の別のコピーが必要ですか？クローンを作成しましょう。これにより、VM のディスクと構成の完全なコピーが作成されます。

**ステップ 1: クローンの開始**

. **rhel9-vm** 詳細ページで、**Actions** -> **Clone** をクリックします
+
image::virt-actions-clone.png[Actions dropdown with Clone option highlighted, link=self, window=blank]
. 名前を `rhel9-vm-clone` に変更します
. **Start VirtualMachine once created** チェックボックスをオンにします
. **Clone** をクリックします
+
image::virt-clone-config.png[Clone VirtualMachine dialog with name and configuration, link=self, window=blank]

**ステップ 2: クローン進行状況の観察**

ダイアログにクローンの進行状況が表示されます： **Request sent** -> **In process** -> **Created**:

image::virt-clone-in-progress.png[Clone progress showing In process status, link=self, window=blank]
完了すると、コンソールはクローンの詳細ページに移動します。左側のサイドバーに両方の VM が表示されます：

image::virt-clone-complete.png[Clone complete showing both rhel9-vm and rhel9-vm-clone in the VM list, link=self, window=blank]
クローンには独自の独立したディスクがあり、一方の変更が他方に影響を与えることはありません。これがゴールデンイメージの作成方法です。希望通りに VM を構成し、環境ごとにクローンを作成します。

IMPORTANT: 続行する前に、左側のサイドバーで **rhel9-vm** をクリックして戻ってください。次のステップ（スナップショットとリストア）は、クローンではなく元の VM で行う必要があります。

=== スナップショット

すべての運用チームは、何かを破壊してしまったパッチに苦しめられた経験を持っています。スナップショットは安全網を提供します。変更前に VM のディスクと構成をキャプチャし、問題が発生した場合は数秒でロールバックできます。

**ステップ 1: スナップショットの取得**

. **rhel9-vm** （クローンではない方）に移動し、その詳細ページを開きます。 **Actions** -> **Take snapshot** をクリックします
+
image::virt-actions-snapshot.png[Actions dropdown with Take snapshot option, link=self, window=blank]
. デフォルト名のままにし（`rhel9-vm-snapshot`）、**Save** をクリックします
+
image::virt-snapshot-config.png[Take snapshot dialog with default name and disk selection, link=self, window=blank]
NOTE: `cloudinitdisk` が含まれていないという警告は予期された動作です。cloud-init は初回起動時にのみ実行され、キャプチャする必要はありません。

**ステップ 2: スナップショットの検証**

**Snapshots** タブをクリックします。完了するとスナップショットのステータスに **Ready** と表示されます：

image::virt-snapshot-ready.png[Snapshots tab showing rhel9-vm-snapshot with Ready status, link=self, window=blank]
**ステップ 3: 意図的に変更を加える**

スナップショットはあなたの安全網です。VM を変更してそれが機能することを証明しましょう。まず、VM ログイン認証情報を取得します：

[source,bash,role="execute"]
----
DATA=$(oc get vm rhel9-vm -n vm-demo -o jsonpath='{.spec.template.spec.volumes[?(@.name=="cloudinitdisk")].cloudInitNoCloud.userData}')
echo "Username: $(echo "$DATA" | grep 'user:' | awk '{print $2}')"
echo "Password: $(echo "$DATA" | grep 'password:' | awk '{print $2}')"
----

VM コンソールに接続します：

[source,bash,role="execute"]
----
virtctl console rhel9-vm -n vm-demo
----

接続後、**Enter** を押してログインプロンプトを表示させます。上記の認証情報でログインし、VM 内部で以下のコマンドを実行して、復元後に検証できる変更を加えます：

[source,bash]
----
touch /home/rhel/important-data.txt
cat /etc/hostname
sudo hostnamectl set-hostname broken-vm
cat /etc/hostname
----

ホスト名が `rhel9-vm` から `broken-vm` に変更されたことが確認できるはずです。完了したら、**Ctrl+5** を押してコンソールを抜けるか、Terminal タブの **再読み込みボタン** をクリックして通常のターミナルに戻ります。

これで VM が変更されました（新しいファイルが存在し、ホスト名が変更されています）。スナップショットに復元し、両方の変更が元に戻ることを証明しましょう。

**ステップ 4: スナップショットからの復元**

. VM を**停止**させます - 右上のアクションボタンにある **Stop** ボタン（四角アイコン）をクリックします
. VM に **Stopped** と表示されたら、**Snapshots** タブに移動し、スナップショットの隣にあるケバブメニュー（3 つの点）をクリックして、**Restore VirtualMachine from snapshot** を選択します
+
image::virt-snapshot-restore-menu.png[Snapshot kebab menu showing Restore VirtualMachine from snapshot option, link=self, window=blank]
. **Restore** をクリックして確認します
+
image::virt-restore-confirmation.png[Restore snapshot confirmation dialog, link=self, window=blank]
. **Start** ボタン（再生アイコン）をクリックして、VM を再度**起動**します

VM が起動したら、ログイン認証情報を再度取得します：

[source,bash,role="execute"]
----
DATA=$(oc get vm rhel9-vm -n vm-demo -o jsonpath='{.spec.template.spec.volumes[?(@.name=="cloudinitdisk")].cloudInitNoCloud.userData}')
echo "Username: $(echo "$DATA" | grep 'user:' | awk '{print $2}')"
echo "Password: $(echo "$DATA" | grep 'password:' | awk '{print $2}')"
----

VM コンソールに接続します：

[source,bash,role="execute"]
----
virtctl console rhel9-vm -n vm-demo
----

NOTE: 起動出力（カーネルメッセージ、systemd サービス）がスクロール表示される場合があります。`rhel9-vm login:` プロンプトが表示されるのを待ち、必要に応じて **Enter** を押してください。前のコマンドの認証情報を確認するために上へスクロールできない場合は、`Ctrl+]` を押してコンソールを抜け、Terminal タブを再読み込みして認証情報コマンドを再実行してください。

認証情報でログインし、復元が成功したことを確認します：

[source,bash]
----
ls /home/rhel/important-data.txt
cat /etc/hostname
----

`ls` では `No such file or directory` と表示され、作成したファイルが消えているはずです。 `cat /etc/hostname` では `broken-vm` ではなく `rhel9-vm` （元のホスト名）が表示され、ホスト名の変更が元に戻っているはずです。ディスクはスナップショットを取得したときの正確な状態に復元されました。このようにして、最初から作り直すことなく、失敗した OS パッチや破損した構成変更をロールバックします。

Terminal タブの **再読み込みボタン** をクリックしてコンソールを抜けます。

== クリーンアップとまとめ

=== まとめ

[cols="1,2"]
|===
|機能 |運用にとっての意味

|**VM は Pod**
|同じ `oc` コマンド、同じスケジューラー、同じ RBAC

|**InstanceTypes**
|クラウドスタイルのプロビジョニング - サイズを選び、イメージを選び、デプロイする

|**同じネットワーク**
|Service や Route は VM とコンテナで同様に機能する

|**同じモニタリング**
|Prometheus ダッシュボードで VM とコンテナのメトリクスを一緒に表示する

|**ライブマイグレーション**
|VM のダウンタイムなしでメンテナンスのためにノードをドレインする

|**クローン**
|開発/テスト/ステージング用にゴールデンイメージから迅速にプロビジョニングする

|**スナップショット**
|パッチ適用やアップグレード前の特定時点へのロールバック
|===

**価値:** 1つのプラットフォーム上で VM とコンテナを並行して実行できます。1セットのツール、1セットのスキルです。準備ができたら Migration Toolkit for Virtualization (MTV) を使用して既存の VM を移行することも、無期限で実行することもできます。OpenShift はその両方をサポートしています。Windows Server は SVVP 認定されており、RHEL/Fedora/CentOS は事前キャッシュされたイメージから数秒で起動します。

=== クリーンアップ

VM ディスクとネームスペースの削除には数分かかります。これはバックグラウンドで実行されるため、すぐに次のモジュールに進むことができます。

[source,bash,role="execute"]
----
(
  virtctl stop rhel9-vm -n vm-demo 2>/dev/null || true
  virtctl stop rhel9-vm-clone -n vm-demo 2>/dev/null || true
  sleep 10
  oc delete namespace vm-demo --ignore-not-found --wait=false
) &>/dev/null & disown
echo "Cleanup running in background - you can continue to the next module"
----
